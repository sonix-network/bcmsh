Embedded applications

Some switch features are not run by the SDK on the host CPU but by firmware on processors inside the switch chip. Broadcom calls these firmware images embedded applications, or eApps. This chapter describes which eApps exist for Trident 3, how the SAI loads them, what SONiC images ship, and how to see from the shell whether one is running. It also covers the processors, memory map and firmware files available to custom applications.

Embedded cores

Trident 3 has two ARM Cortex-R5 cores for eApps, uC 0 and uC 1. The shell’s MCS commands (MCSStatus, MCSLoad, MCSMsg, MCSCmd, MCSDump, MCSTimeStamp) work on these cores. Each core runs one application at a time on top of Broadcom’s small firmware kernel, the uKernel. The SDK talks to the application over a message channel; a feature module such as IFA or BFD only works once its application answers on that channel.

A core stays in reset until an eApp is loaded onto it. MCSStatus then shows RESET. This is the normal state on a switch whose SONiC image loads no eApps, and does not mean the core is faulty.

The chip also has Cortex-M0 cores (see M0). These are separate processors: on SONiC Trident 3 switches core 0 runs the link-scan and LED firmware, independent of the eApps.

Capabilities

An eApp can do work close to the switch hardware while the host SDK manages normal switching. Besides the packaged telemetry and time-synchronisation applications below, custom firmware can:

  • Exchange control messages and bulk data with the host.

  • Read switch registers and counters over the S-channel, for example to sample a counter periodically without a host request for every sample.

  • Transmit Ethernet packets and receive packets steered to its CPU queue.

  • Keep results in shared SRAM for the host to read.

A custom application has run on two Trident 3 switches, sampling counters every 100 ms and exchanging one discovery packet per second between them. Both cores can run custom applications concurrently. These examples show control and monitoring uses; they do not establish line-rate packet processing. Receiving packets requires queue steering, and an application must coordinate its DMA channels and other resources with the host SDK. Loading firmware alone does not configure those paths.

Processor specifications

The following configuration was measured on BCM56870 A0 switches. The clock is approximate; do not use it as a guaranteed frequency for every platform.

Property

Configuration

Application processors

Two ARM Cortex-R5 r1p3 cores, ARMv7-R

Instruction sets and data

ARM (A32) and Thumb-2; little-endian data

Measured CPU clock

Approximately 858 MHz

Instruction TCM (ATCM), per core

128 KiB

Data TCM (BTCM), per core

256 KiB, ECC-protected

L1 caches, per core

16 KiB instruction and 16 KiB data; four-way, 32-byte cache lines

Memory protection

MPU with 16 regions

Shared RTS SRAM

1 MiB, accessible by both R5 cores and the host

TCM is tightly coupled memory local to a processor. It is separate from both the shared SRAM and the switch’s packet buffer. Cache sizes describe the hardware; firmware decides whether to enable caches. Custom firmware must initialise its BTCM with word stores before using unwritten memory: accessing uninitialised ECC memory can fault.

ATCM holds the exception vectors, code and read-only data. BTCM holds writable data and stacks. Shared SRAM supports host communication and application data, but includes SDK messaging storage: an application must reserve that storage rather than treating the whole megabyte as free. The M0 LED/link-scan processors have their own memory and firmware.

Firmware files

The R5 images discussed here use Motorola S-record files (.srec). These are text files describing bytes to write at specified addresses; they are not raw binaries or ELF executables. A core-specific filename such as BCM56870_0_ifa2.srec identifies the intended chip and core, but does not by itself prove compatibility with the installed SDK or CANCUN version.

The examined IFA2, Mirror on Drop and OneSync files contain:

  • An S0 header naming the file.

  • S3 data records with 32-bit addresses, payload bytes and record checksums.

  • An S7 termination record carrying an entry address.

Their data spans code in ATCM, initial data in BTCM and initial messaging storage in shared SRAM. The S-record container describes loading; the firmware inside it must also implement the SDK’s startup and messaging contract. Converting arbitrary ARM code to S-record text is insufficient.

For MCSLoad, keep each data record’s payload length a multiple of four bytes. An unaligned payload can fail with record Not Multiple of 4. Choose the image built for the target core. Some stock files also initialise shared messaging storage for both cores, so loading one can affect communication with an application on the other.

The R5 S-record files are separate from M0 .bin firmware, PCIe-loader images and CANCUN .pkg files; these formats and execution domains are not interchangeable.

Applications for Trident 3

Broadcom builds the following eApps for BCM56870/BCM56873. Each is built once per core, as BCM56870_0_<name>.srec for uC 0 and BCM56870_1_<name>.srec for uC 1.

Feature name

Image

What it does

IFA2

ifa2

IFA 2.0, in-band flow analysis (telemetry inserted into data packets). Tied to specific CANCUN versions.

IFA

ifa

IFA 1.0, the earlier version of the same feature.

MOD (Mirror on Drop) on top of the flow tracker: reports packets the switch drops.

The same configuration files also list an IFACC image (ifacc.bin) that runs on an M0 core rather than an R5 core.

Other SDK features are eApp-based as well, among them BFD, BroadSync and TX beacons (txbeacon). No Trident 3 image for these is listed in the SONiC configuration files described below.

The eApp configuration file

The Broadcom SAI loads eApps itself; normally nothing has to be typed in the shell. It reads a JSON file named by the configuration variable sai_eapp_config_file (normally /etc/broadcom/eapps_cfg.json). The file has a directory and a list of applications:

{
   "json-version" : 1,
   "embedded-apps-location" : "/usr/lib/eapps",
   "embedded-apps" : [
       {
           "feature-names" : ["IFA2"],
           "file-name" : "BCM56870_0_ifa2.srec",
           "app-version" : "4.4.4.0",
           "compatible-silicon" : ["BCM56870", "BCM56873"],
           "compatible-cancun" : ["06.13.00"],
           "r5-core-affinity" : [0],
           "load-at-init" : 0
       }
   ]
}

Key

Meaning

embedded-apps-location

Directory that holds the image files.

feature-names

The SAI feature the image provides (IFA2, MOD, PTP …).

file-name

Image file in that directory.

app-version

Expected application version.

compatible-silicon

Chips the image is built for. Entries for other chips are skipped.

compatible-cancun

CANCUN versions the image works with, if the list is present. If the loaded CANCUN is not in it, the SAI logs The current Cancun is not in the compatible-cancun list.

r5-core-affinity, m0-core-affinity

Which embedded core the image runs on.

load-at-init

1 loads the image while the switch initialises, 0 when the feature is configured. IFA cannot be loaded at initialisation (Loading IFA firmware during Init is not supported.).

BCMSAI dump_eapp_config prints the configuration the SAI has read. If it prints only an empty embedded-apps-location: line, the SAI has no eApp configuration and will load nothing.

Loading

When a feature needs its application, the SAI checks the entry against the chip and CANCUN version, loads the image onto the core named in the file with the shell command MCSLoad (mcsload <core> <dir>/<file> InitMCS=true, or StartUC=true), and then starts the SDK feature module. For PTP it then also runs onesync init. Unloading stops the core’s messaging (MCSMsg).

The SDK feature module finds the application over the message channel. If no application answers, it logs a warning such as uKernel BFD application not available or uKernel IFA application not available and carries on without the feature. These messages at start-up are harmless on a switch that does not use the feature.

Some features also need a configuration variable. IFA needs ifa_enable set to 1; without it the SDK skips IFA set-up and the SAI logs ifa_enable config property is disabled.. The flow-tracker applications need flowtracker_enable.

SONiC images

What a switch runs depends on its SONiC image:

  • Community SONiC builds, including the one on the switches described in Example validation, ship no eApp images. The SAI package still contains a sample eApp configuration, but it points to a directory that does not exist, and the configured sai_eapp_config_file is missing. Both cores stay in RESET and BCMSAI dump_eapp_config prints an empty configuration. Features that need an eApp (IFA, Mirror on Drop, the flow tracker application, PTP, BroadSync, BFD offload) have no firmware to talk to; their shell commands report that the firmware is not loaded or that the feature is not initialised.

  • Broadcom’s enterprise SONiC ships the eApps in three packages in the syncd container, embedded-apps-ifa (IFA2), embedded-apps-mod (MOD) and embedded-apps-timesync (OneSync PTP), installed in /usr/lib/eapps, and the configuration file /etc/broadcom/eapps_cfg.json on the host, which is mapped into the syncd container. Its Trident 3 common configuration sets sai_eapp_config_file and ifa_enable. All entries load on demand, so the cores stay in reset until a feature such as IFA is configured.

Checking eApp state

These commands are read-only:

  • MCSStatus shows each core’s state: RESET with no application, Ok with the application’s version and name when one runs. mcsstatus Quick=true pings the cores instead.

  • BCMSAI dump_eapp_config shows the eApp configuration the SAI has read.

  • config show with ifa, flowtracker or sai_eapp shows the related configuration variables.

  • MCSDump with a core number shows the thread table of a running application.

On a switch without eApps both cores are in reset:

Hardware-validated

drivshell> mcsstatus
uC 0 status: RESET
uC 1 status: RESET

Hardware-validated: No eApp configuration

drivshell> BCMSAI dump_eapp_config
embedded-apps-location:

With an application loaded, MCSStatus reports the core as Ok and prints the application’s version string, which ends in the feature name. This is the IFA 2.0 application on uC 0:

Hardware-validated

drivshell> mcsstatus
uC 0 status: Ok
version:  4.4.4.0 EA1 Wed Dec  6 18:05:42 PST 2023 IFA2
uC 1 status: RESET

Loading an eApp by hand

MCSLoad loads an image from a file inside the syncd container. Give InitMCS=true on the first load, as the SAI does, to initialise the subsystem. On success the shell reports that the core’s messaging is up:

Hardware-validated

drivshell> mcsload 0 /root/BCM56870_0_ifa2.srec InitMCS=true
UC0 messaging system: up

Use the BCM56870 image built for the core you load it onto (BCM56870_0_… for uC 0). Loading it does not configure the feature: the SDK module must still be initialised, with its configuration variable set, before the feature does anything. A hand-loaded application is gone after syncd restarts: both cores are back in reset. In-band Flow Analyzer (IFA 2.0) shows a full example with the IFA 2.0 application.

Warning

Loading firmware by hand changes the switch behind SONiC’s back. MCSLoad resets the core first, so any feature already running on that core stops. Use it only on a test switch.
