FieldProcessor

Manage Field Processor

FieldProcessor

Shortest form: fp.

Manage the Field Processor (FP): the TCAM classifier that matches packet fields (qualifiers) and applies actions such as drop, copy to CPU, redirect, police and count. Rules live in groups (one or more TCAM slices with a fixed qualifier set) and are made of entries. On Trident 3 there are lookup (VFP), ingress (IFP), egress (EFP) and exact-match stages. The usual abbreviation is fp.

How the arguments work:

  • Sub-command keywords must be typed in full: fp entry create works, fp ent create does not. Case does not matter. Only fp itself can be abbreviated. Name=value parameters (PolId=, StatId= …) can be shortened to their upper-case letters as usual.

  • IDs and numbers can be decimal or 0x hex.

  • Qualifier and action names are the SDK names without their prefix, for example DstIp, InPort, L4DstPort, Drop and CopyToCpu. Case does not matter. fp list qualifiers and fp list actions list them.

  • fp qset … builds a qualifier set that the shell remembers between commands. fp group create and fp group set use it.

  • fp alone, or an unknown sub-command, prints the usage.

Where the built-in help differs: it lists a top-level status, but the shell does not accept it (fp status prints the usage); use fp group status <gid>. Several working forms are missing from the help: group status, group mode, group lookup, list user, qual <eid> <QUAL> ?, show qset, show presel and show wbcachesize. list quals is accepted for list qualifiers. The help line sanity works only on chips that support it.

Warning

On SONiC the FP belongs to the SAI. ACL tables and rules, and the CoPP traps that send control packets (LLDP, BGP, ARP …) to the CPU, are FP groups and entries. fp init, fp detach, fp entry destroy with no ID, and fp policer destroy all delete them, so control-plane traffic stops reaching the CPU until syncd is restarted. Any other change made here is invisible to SONiC and may be overwritten, or may make later ACL updates fail. The show, list and get forms are read-only.

What a SONiC switch has in the FP: group 1 on the ingress stage holds the CoPP traps and ACL rules (entries with GpCopyToCpu, CosQCpuNew, RpDrop, Drop and policers), group 2 on the lookup stage holds a handful of DoNotLearn/DoNotCheckVlan entries, and group 3 on the egress stage is empty. Range checker 1 also belongs to SONiC. Pick IDs well away from these (the examples here use group 100, entry 1000 and range 100) and remove what you create.

When an FP call fails, the shell prints FP(unit 0) Error: <function>() failed: <reason> and then Failed to execute the diagnostic command. Error: Operation failed.; bcmcmd still exits 0. Entry not found means the entry, group, counter or action named does not exist.

Hardware-validated: Build a drop rule by hand (changes the ASIC)

drivshell> fp qset clear
drivshell> fp qset add DstIp
BCM_FIELD_QSET_ADD(DstIp) okay
drivshell> fp group create 10 100
drivshell> fp entry create 100 1000
drivshell> fp qual 1000 DstIp 192.0.2.1 255.255.255.255
drivshell> fp action add 1000 Drop
drivshell> fp entry install 1000

Each step prints nothing on success. fp show entry 1000 then shows the installed entry. Remove it again with fp entry destroy 1000, fp group destroy 100 and fp qset clear.

Show

FieldProcessor show [brief]

Without an argument, dump every group and entry with their qualifiers, actions, policers and counters. brief prints a short summary per group. Read-only.

On Trident 3 the dump starts with the range checkers and the TCAM size of each stage (ingress 12 slices, egress 4, lookup 4), then each group with its mode, stage, port bitmap, qualifier set, select codes and group_status, followed by its entries. Each entry shows its slice, priority, flags, qualifiers with DATA/MASK, one action={…} line per action, its policer and its counter (statistics={stat id <n> …}). A SONiC switch prints about 1800 lines. brief keeps the group headers and leaves out the entries.

Output from older Trident+ (BCM56846) switches is in EdgeNOS: How Cumulus/switchd programs an ACL in the BCM56846 FP (+ raw fp show / FP_TCAM captures) and Edgecore AS5610-52X reverse engineering: Cumulus 2.5 baseline captures.

FieldProcessor sanity

Run the FP software/hardware consistency check, on chips that support it. On other chips the shell prints the usage. The check may change field processor state, so do not run it on a production switch.

Unvalidated

drivshell> fp sanity

Module control

FieldProcessor init

Re-initialise the FP. This deletes every group, entry, range, policer and counter, and clears the shell’s qualifier set.

Warning

On SONiC this removes all ACLs and CPU traps.

sonic-mgmt test suite files invoking bcmcmd (19 files) uses fp detach followed by fp init on test switches.

Unvalidated

drivshell> fp init
FieldProcessor detach

Shut the FP down. FP commands then fail until fp init.

Warning

On SONiC this removes all ACLs and CPU traps.

Unvalidated

drivshell> fp detach
FieldProcessor resync

Rebuild the SDK’s FP state from the hardware, as done after a warm boot. Changes SDK state.

Unvalidated

Qualifiers and actions

FieldProcessor qual <eid> <QUAL> [<udf_id> | <data_qual_id>] <data> <mask>

Set a qualifier of an entry. The format of data and mask depends on the qualifier: IP addresses and masks, MAC addresses, port bitmaps (InPorts), numbers, or names for enumerated qualifiers (IpType, L2Format, Color …). Other forms:

  • qual <eid> <QUAL> ? (or show) prints the table of all qualifiers of all stages (FP STAGE: All, about 1700 lines) with the data and mask format of each; find the line of your qualifier in it. Read-only.

  • qual <eid> delete <QUAL> removes one qualifier from the entry.

  • qual <eid> clear removes all of them.

Reinstall the entry for a change to reach hardware.
