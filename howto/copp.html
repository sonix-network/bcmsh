Protecting the CPU with CoPP

Control-plane policing (CoPP) decides which packets the switch chip sends to the CPU, on which CPU queue, and how fast. It keeps a flood of ARP or BGP packets from starving bgpd, lldpd or the kernel.

Trident 3 has no separate CoPP block. The SAI builds SONiC’s CoPP from three ordinary SDK features:

  • Field Processor entries in the ingress stage (IFP), one or more per trap, that match the protocol and copy or redirect it to the CPU;

  • FP policers (meters), one per trap group, that colour packets green or red against the group’s rate; only green packets are copied to the CPU;

  • CPU CoS queues: the entry’s CosQCpuNew action picks the queue, which is the queue of the trap group.

Packets that reach the CPU are then handed to the EthernetN netdev of the port they arrived on by a KNET filter (see KNET and the CPU port).

Everything on this page is read-only unless stated otherwise.

From SONiC trap groups to FP entries

SONiC’s CoPP configuration (/etc/sonic/copp_cfg.json, overridable in COPP_TABLE and COPP_GROUP of config_db) lists traps, each in a trap group with an action, a queue and a rate:

How to read it:

prio=0x4

The trap priority from SONiC. Within a group, the matching entry with the highest priority wins.

GpCopyToCpu, CosQCpuNew 4

Copy green packets to the CPU, on CPU queue 4. The Gp, Yp and Rp prefixes make an action apply only to green, yellow or red packets.

RpDrop, UnmodifiedPacketRedirectPort 0x8000000

Drop red packets, and redirect the original packet to the CPU port (0x8000000 is the CPU port as a gport), so it is not also forwarded. This is SONiC’s trap action. A copy trap such as ARP has only GpCopyToCpu and YpCopyToCpu: the packet is still switched normally and the CPU gets a copy.

policer=

The trap group’s meter. With PacketBased=0x1 the commit_kbits_sec and commit_kbits_burst fields are packets per second and packets: 0x64 is 100/s with a burst of 100, the lldp group’s CIR and CBS. Every entry of the trap group points at the same policer, so the rate is shared by all its protocols (LLDP, UDLD and DHCP here).

statistics=

The counter. The entries of a trap group share one counter, so it counts all packets of the group, not only this entry’s.

Its priority (2) is higher than ip2me (1), so it wins for UDP 4789. Drop alone would not stop the copy to the CPU; CopyToCpuCancel does. The same rule applies to ACLs (see A DROP rule that still lets packets reach the CPU).

Counting what reaches the CPU

There are three places to count, in packet order:

  1. The trap group’s FP counter, with fp stat get. The StatId is the stat id in the entry. GreenPackets went on to the CPU, RedPackets were dropped by the policer.

  2. The CPU queue counters, with show counters on cpu0: MC_PERQ_PKT(<queue>) counts packets queued to the CPU, PERQ_DROP_PKT(<queue>) packets the queue had to drop.

  3. The netdev in Linux (ip -s link show EthernetN, tcpdump).

The ARP entries (15–20) use stat 12. Read it, send 3000 ARP requests to the switch at about 5600 packets per second, and read it again:

Hardware-validated: The ARP group’s counter and CPU queue 4 during an ARP flood

drivshell> fp stat get StatId=12 type=Packets
The value is: 0x00000003f
drivshell> fp stat get StatId=12 type=GreenPackets
The value is: 0x00000003f
drivshell> fp stat get StatId=12 type=RedPackets
The value is: 0x000000000
drivshell> fp stat get StatId=12 type=Packets
The value is: 0x000000bf7
drivshell> fp stat get StatId=12 type=GreenPackets
The value is: 0x0000003d9
drivshell> fp stat get StatId=12 type=RedPackets
The value is: 0x00000081d
drivshell> show counters nz cpu0
MC_PERQ_PKT(4).cpu0      :               796,013              +1,016               3/s
MC_PERQ_BYTE(4).cpu0     :           110,657,609             +75,722             355/s

The counter went up by 3000 (0xbf7 - 0x3f): 922 green and 2077 red, plus one background ARP packet that arrived between the reads. The policer let through its burst of 600 packets plus 600 per second for the half second the flood lasted; the rest were dropped before they reached a queue. CPU queue 4 received the green ARP packets plus the group’s other traffic (LLDP, LACP, BGP), and PERQ_DROP_PKT stayed at zero, so the CPU queue itself never overflowed.

The counter values are cumulative and in hex. show counters prints the change since the last show counters call as the second number.

Why doesn’t my protocol reach the CPU?

Work from SONiC down to the netdev:

  1. show copp configuration: is the trap listed and installed? not-installed means SONiC did not create it (for example sample_packet without sFlow); there is no FP entry then.

  2. fp show group 1: find the entry by its qualifiers (EtherType, destination MAC, L4 port). Is it Installed, Enabled?

  3. Send the packet and read the group’s fp stat. No increase means the packet does not match: check the qualifiers against the packet (VLAN tags, destination MAC, whether the destination is really one of the switch’s own addresses for ip2me and BGP).

  4. RedPackets rising means the policer is dropping. Rate-limit the sender or raise the group’s cir/cbs in SONiC.

  5. MC_PERQ_PKT of the group’s queue on cpu0 rising, but PERQ_DROP_PKT also rising, means the CPU is not draining the queue.

  6. Queue counters rise but tcpdump sees nothing: check knetctrl filter show. SONiC has one filter per port (ingport=xe3 → Ethernet11); a port without a filter has no netdev to deliver to.

drivshell> knetctrl filter show

Changing CoPP

Change rates and queues in SONiC (COPP_GROUP in config_db); SONiC updates the policer and the entries. The shell can change the same objects (fp policer set, fp action add), but SONiC does not see those changes, a later SONiC update can overwrite them, and a mistake can cut the switch off from its control plane.

Warning

Never run fp policer destroy all, fp entry destroy without an entry ID, fp group destroy 1 or fp detach on a running switch: they remove the CoPP entries and policers, and LACP, LLDP, ARP and BGP stop reaching the CPU until syncd is restarted.

To try your own match-and-copy rules without touching SONiC’s entries, build them in a group of your own, as in Copy or mirror matching packets to the CPU.
