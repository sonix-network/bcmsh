Debugging ACL rules

SONiC ACLs (ACL_TABLE and ACL_RULE in config_db) end up in the same Field Processor as CoPP (see Protecting the CPU with CoPP). This page shows how a SONiC ACL looks in the shell, how to check that a rule matches and what it does to the packet, and how to build a rule of your own that copies, mirrors or rate-limits matching packets to the CPU.

The mapping is:

SONiC

Field Processor

ACL table (ACL_TABLE)

An FP group, with a qualifier set for the table type and its own TCAM slices

Table binding (ports)

An InPorts qualifier on every entry

Rule (ACL_RULE)

An FP entry; the rule’s PRIORITY is the entry priority

Rule counter (aclshow)

An FP counter (stat) attached to the entry

PACKET_ACTION

FORWARD: no action (the rule only counts); DROP: Drop

An example ACL

A table bound to Ethernet11 with one rule that only counts ICMP from a test host and one that drops UDP to port 5000:

{
  "ACL_TABLE": {
    "TESTACL": {"type": "L3", "stage": "ingress", "ports": ["Ethernet11"],
                "policy_desc": "bcmsh how-to test table"}
  },
  "ACL_RULE": {
    "TESTACL|COUNT_ICMP": {"PRIORITY": "30", "SRC_IP": "198.51.100.10/32",
                           "IP_PROTOCOL": "1", "PACKET_ACTION": "FORWARD"},
    "TESTACL|DROP_UDP5000": {"PRIORITY": "20", "IP_PROTOCOL": "17",
                             "L4_DST_PORT": "5000", "PACKET_ACTION": "DROP"}
  }
}

admin@sonic:~$ sudo config load -y testacl.json
admin@sonic:~$ show acl rule
Table    Rule          Priority    Action    Match                     Status
-------  ------------  ----------  --------  ------------------------  --------
TESTACL  COUNT_ICMP    30          FORWARD   IP_PROTOCOL: 1            Active
                                             SRC_IP: 198.51.100.10/32
TESTACL  DROP_UDP5000  20          DROP      IP_PROTOCOL: 17           Active
                                             L4_DST_PORT: 5000

Finding the table in the shell

A new table is a new FP group. fp show lists the groups; compare it with the list before the table was created. Here group 4 is new (groups 1–3 belong to SONiC’s CoPP and internal entries):

Hardware-validated

drivshell> fp show group 4 brief
GID          4: gid=0x4, mode=Double, stage=Ingress lookup=Enabled, ActionResId={-1}, pbmp={0x…}
         qset={SrcIp, DstIp, InPorts, RangeCheck, L4SrcPort, L4DstPort, EtherType, IpProtocol, TcpControl, IpType, Stage, StageIngress, IcmpTypeCode, Vpn, _InPorts_1, _InPorts_2},
         selcodes[0]=
{ {SrcIp->InPorts->RangeCheck->L4SrcPort->EtherType->TcpControl->IpType->IcmpTypeCode->_InPorts_2},
         selcodes[1]=
{ {DstIp->RangeCheck->L4DstPort->IpProtocol->IpType->Vpn->_InPorts_1},

         slice_pri= 100    {slice_number=3, Entry count=768(0x300), Entry free=766(0x2fe)},
         slice_sec = {slice_number=4}
         group_status={prio_min=20, prio_max=30, entries_total=2304, entries_free=2302,
                       counters_total=83968, counters_free=57854, meters_total=6144, meters_free=5376}

qset is what the table type can match on (an L3 table: addresses, ports, protocol, TCP flags, ICMP type). The group is double-wide and has TCAM slices 3 and 4 to itself; prio_min/prio_max are the lowest and highest rule priorities in it.

Each rule is one entry, in priority order. The ICMP rule:

Hardware-validated

drivshell> fp show entry 0x24
EID 0x00000024: gid=0x4,
 slice=3, slice_idx=0, part=0, prio=0x1e, flags=0x10602, Installed, Enabled, color_indep=1
 slice=4, slice_idx=0, part=1, prio=0x1e, flags=0x10604, Installed, Enabled, color_indep=1

 SrcIp
    Part:0 Offset0: 48 Width0:  16
    Part:0 Offset1: 64 Width1:  16
    DATA=0xc633640a
    MASK=0xffffffff
 InPorts
     DATA=0x…0000000000001000
     MASK=0x…000222222223e23
 …
 IpProtocol
    Part:1 Offset0: 80 Width0:   4
    Part:1 Offset1: 84 Width1:   4
    DATA=0x00000001
    MASK=0x000000ff
         policer=
         statistics={stat id 15  slice = 9 idx=3 entries=1}{Packets}{Bytes}

Check:

  • Installed, Enabled: the entry is in hardware.

  • prio=0x1e: priority 30, the rule’s PRIORITY.

  • The qualifiers: SrcIp 0xc633640a is 198.51.100.10 with a /32 mask, IpProtocol 1 is ICMP. Values are in hex.

  • InPorts: a bitmap of port numbers. Bit 12 is set in DATA: port 12, xe3 (ps prints the number in brackets), which is Ethernet11. The mask covers every front-panel port, so the entry matches only on xe3.

  • No action= line: FORWARD only counts. The DROP rule’s entry has action={act=Drop, …}.

  • stat id 15: the counter.

Is the rule matching?

Read the entry’s counter with fp stat get before and after sending traffic. SONiC’s aclshow reads the same counter:

Hardware-validated

drivshell> fp stat get StatId=15 type=Packets
The value is: 0x000000000
drivshell> fp stat get StatId=16 type=Packets
The value is: 0x000000000
drivshell> fp stat get StatId=15 type=Packets
The value is: 0x00000000a
drivshell> fp stat get StatId=16 type=Packets
The value is: 0x000000064

admin@sonic:~$ aclshow -a
RULE NAME     TABLE NAME      PRIO    PACKETS COUNT    BYTES COUNT
------------  ------------  ------  ---------------  -------------
COUNT_ICMP    TESTACL           30               10           1020
DROP_UDP5000  TESTACL           20              100           6400

aclshow is only updated every 10 seconds (counterpoll show, ACL); fp stat get reads the hardware directly. Byte counts include the 4-byte CRC.

If the counter does not move:

  1. show acl table: is the table Active and bound to the port the packets arrive on? Check the InPorts bitmap of the entry.

  2. fp show entry: does every qualifier match the packet? A missing mask bit or a wrong byte order in DATA is easiest to see here.

  3. Within one group only the highest-priority matching entry acts. A broader rule with a higher PRIORITY in the same table hides a narrower one below it; its counter rises instead.

  4. Is there room? crm show resources acl group and crm show resources acl table show how many tables and entries are used and left. On a Trident 3 the ingress stage has 12 TCAM slices (fp show prints tcam_slices=12) shared by CoPP, SONiC’s own groups and every ACL table, and a double-wide table takes two:

    admin@sonic:~$ crm show resources acl group
Stage    Bind Point    Resource Name      Used Count    Available Count
-------  ------------  ---------------  ------------  -----------------
INGRESS  PORT          acl_group                   1               1023
INGRESS  PORT          acl_table                   1                  3
…
admin@sonic:~$ crm show resources acl table
Table ID         Resource Name      Used Count    Available Count
---------------  ---------------  ------------  -----------------
0x70000000006c8  acl_entry                   2               1534
0x70000000006c8  acl_counter                 2              56318

    fp show group <gid> brief shows the same per group as entries_free.

A DROP rule that still lets packets reach the CPU

The UDP packets above were sent to the switch’s own address. The rule counted all 100, yet the packets still arrived in Linux:

admin@sonic:~$ sudo tcpdump -lni Ethernet11 'udp and (port 5000 or port 5001)'
09:04:18.896090 IP 198.51.100.10.40000 > 198.51.100.1.5000: UDP, length 11
09:04:18.948666 IP 198.51.100.10.40000 > 198.51.100.1.5000: UDP, length 11
09:04:19.011570 IP 198.51.100.10.40000 > 198.51.100.1.5001: UDP, length 11
09:04:19.063223 IP 198.51.100.10.40000 > 198.51.100.1.5001: UDP, length 11

Every group in the FP matches each packet in parallel and the actions of all matching entries are applied. The ACL entry’s Drop stops the packet from being forwarded, but the CoPP ip2me entry in group 1 still copies it to the CPU (its counter rose by the 100 dropped packets too). Drop does not cancel a copy to the CPU; CopyToCpuCancel does. Added to the ACL entry from the shell, only the packets to port 5001 still arrive:

Hardware-validated: Stop the copy to the CPU as well (changes a SONiC entry)

drivshell> fp action add 0x25 CopyToCpuCancel
drivshell> fp entry reinstall 0x25
drivshell> fp show entry 0x25
…
         action={act=CopyToCpuCancel, param0=0(0), param1=0(0), param2=0(0), param3=0(0)}
         action={act=Drop, param0=0(0), param1=0(0), param2=0(0), param3=0(0)}
         statistics={stat id 16  slice = 9 idx=2 entries=1}{Packets}{Bytes}
drivshell> fp action remove 0x25 CopyToCpuCancel
drivshell> fp entry reinstall 0x25

Changes to an entry take effect only after fp entry reinstall. This is the same pair of actions that CoPP’s VXLAN exception uses (see Protecting the CPU with CoPP). Remove the action again as shown: SONiC does not know about it.

To keep traffic away from the switch’s own services in SONiC, use a control-plane ACL ("type": "CTRLPLANE"), which SONiC implements in the Linux firewall, not in the FP.

Copy or mirror matching packets to the CPU

The chip sends a packet to the CPU only if CoPP or an ACL tells it to, so tcpdump on an EthernetN normally sees only control traffic. Capturing port traffic with tcpdump mirrors everything on a port; an FP entry of your own copies only the packets you want and leaves SONiC’s entries alone. The packets keep being switched or routed as before.

The steps build group 100 with entry 1000, matching UDP to port 6000 from 198.51.100.10. All of them change the ASIC behind SONiC’s back; remove everything again at the end (Cleaning up). Choose group and entry IDs well away from SONiC’s.

Hardware-validated: A copy-to-CPU entry with a counter, on CPU queue 2

drivshell> fp qset clear
drivshell> fp qset add SrcIp
BCM_FIELD_QSET_ADD(SrcIp) okay
drivshell> fp qset add IpProtocol
BCM_FIELD_QSET_ADD(IpProtocol) okay
drivshell> fp qset add L4DstPort
BCM_FIELD_QSET_ADD(L4DstPort) okay
drivshell> fp group create 10 100
drivshell> fp entry create 100 1000
drivshell> fp qual 1000 SrcIp 198.51.100.10 255.255.255.255
drivshell> fp qual 1000 IpProtocol 17 0xff
drivshell> fp qual 1000 L4DstPort 6000 0xffff
drivshell> fp action add 1000 CosQCpuNew 2
drivshell> fp stat create group=100 type0=Packets type1=Bytes
Stat created with id: 17
drivshell> fp stat attach entry=1000
drivshell> fp entry install 1000
drivshell> fp action add 1000 CopyToCpu 0 0
drivshell> fp entry reinstall 1000

CopyToCpu needs both parameters; fp action add 1000 CopyToCpu alone prints the usage. CosQCpuNew 2 puts the copies on CPU queue 2, away from the queues CoPP uses here (0, 1 and 4), so they are easy to count and do not crowd out control traffic. (SONiC puts sFlow samples on queue 2 when sFlow is enabled; pick another queue then.) fp stat create prints the new counter’s ID; stat attach without StatId uses it.

Packets to an unknown MAC address on the VLAN are now copied to the CPU and appear on the netdev of the port they arrived on, with their VLAN tag:

admin@sonic:~$ sudo tcpdump -lnei Ethernet11 udp port 6000
09:07:33.233801 52:54:00:d5:ca:e0 > 02:00:00:00:99:99, ethertype 802.1Q (0x8100), length 64: vlan 902, p 0, ethertype IPv4 (0x0800), 198.51.100.10.40000 > 198.51.100.1.6000: UDP, length 11
…
5 packets captured

Without the entry the same five packets were not captured. The entry’s counter and CPU queue 2 count them:

Hardware-validated

drivshell> fp stat get StatId=17 type=Packets
The value is: 0x000000005
drivshell> show counters nz cpu0
MC_PERQ_PKT(2).cpu0      :                     5                  +5
MC_PERQ_PKT(4).cpu0      :               797,219                 +60               3/s

Mirror instead of copy

MirrorIngress sends a mirror copy to a port instead. The CPU port works as the mirror-to port; give it by name:

Hardware-validated: Mirror matching packets to the CPU (entry 1000 with its other actions removed)

drivshell> fp action add 1000 MirrorIngress 0 0
FP(unit 0) Error: invalid port string: "0"
Failed to execute the diagnostic command. Error: Operation failed.
drivshell> fp action add 1000 MirrorIngress 0 cpu0
drivshell> fp entry reinstall 1000
drivshell> fp show entry 1000
…
         action={act=MirrorIngress, param0=0(0), param1=134217728(0x8000000), param2=0(0), param3=0(0)}
drivshell> show counters nz cpu0
MC_PERQ_PKT(0).cpu0      :                    23                  +5
MC_PERQ_PKT(4).cpu0      :               797,732                +108               3/s

The first parameter is the module (0), the second the port. Mirrored copies arrive on CPU queue 0 and on the ingress port’s netdev, like copies. mirror dest show already lists a mirror destination on cpu0 on a SONiC switch; MirrorIngress to cpu0 does not add another.

Rate-limit the copies

Copying a heavy flow to the CPU can starve control traffic. Do what CoPP does: attach a packet-based policer and copy only green packets with GpCopyToCpu. A counter with colour types shows what the policer did:

Hardware-validated: 100 copies per second, burst 100

drivshell> fp policer create PolId=100 Mode=SrTcm cir=100 cbs=100 PacketBased=1
drivshell> fp action remove 1000 CopyToCpu
drivshell> fp action add 1000 GpCopyToCpu 0 0
drivshell> fp policer attach entry=1000 level=0 PolId=100
drivshell> fp stat detach entry=1000 StatId=17
drivshell> fp stat destroy StatId=17
drivshell> fp stat create group=100 type0=Packets type1=GreenPackets type2=RedPackets
Stat created with id: 18
drivshell> fp stat attach entry=1000
drivshell> fp entry reinstall 1000

Then send 3000 matching packets as fast as possible (here about 6100 per second) and read the counter:

Hardware-validated

drivshell> fp stat get StatId=18 type=Packets
The value is: 0x000000bb8
drivshell> fp stat get StatId=18 type=GreenPackets
The value is: 0x000000096
drivshell> fp stat get StatId=18 type=RedPackets
The value is: 0x000000b21
drivshell> show counters nz cpu0
MC_PERQ_PKT(2).cpu0      :                   155                +150

Of 3000 packets sent in half a second, 150 were green (the burst of 100 plus 100 per second) and copied; tcpdump on Ethernet11 captured exactly those 150. The counter types must be chosen when the counter is created, so the old counter is detached and replaced.

Cleaning up

Hardware-validated

drivshell> fp stat detach entry=1000 StatId=18
drivshell> fp entry destroy 1000
drivshell> fp stat destroy StatId=18
drivshell> fp policer destroy PolId=100
drivshell> fp group destroy 100
drivshell> fp qset clear

Always give the IDs: fp entry destroy and fp policer destroy all without them also remove SONiC’s ACL and CoPP entries. fp qset clear resets the shell’s qualifier set, which the next fp group create would otherwise reuse.
