VXLAN tunnels

On a SONiC Trident 3 switch with a VXLAN hardware SKU, the chip encapsulates and decapsulates VXLAN itself. SONiC programs the tunnels through the SAI, which uses the SDK’s flow API on this chip (the classic bcm_vxlan API is not available). There is no diag-shell command to create a VXLAN tunnel by hand; this page shows how to see what SONiC programmed and how to check that packets are really encapsulated and decapsulated in hardware.

The example stretches VLAN 100 between two switches over VNI 10100. Each switch has one host in the VLAN, and the switches reach each other’s tunnel address (VTEP) over a routed link.

Requirements

VXLAN needs flex flows (flow_init_mode=1) and RIOT (riot_enable=1) in the switch’s config.bcm, plus sai_tunnel_support=1 for the SAI. Not every SONiC SKU sets them. Check with config show:

Hardware-validated

drivshell> config show flow
    flow_init_mode=1

The SAI’s tunnel summary says whether VXLAN is available and how many tunnels are in use (see BCMSAI MPTnl):

tnl(curr:2…) and vxlan(curr:2…) count the local VTEP and one tunnel to a remote VTEP; vlan(curr:1…) is one VLAN-to-VNI mapping.

The SONiC side

The tunnel is configured in SONiC, not in the diag shell. On sw2 (sw4 uses its own addresses):

$ sudo config loopback add Loopback0
$ sudo config interface ip add Loopback0 198.18.255.2/32
$ sudo config interface ip add Ethernet112 198.18.0.0/31
$ sudo config route add prefix 198.18.255.4/32 nexthop 198.18.0.1
$ sudo config vxlan add vtep 198.18.255.2
$ sudo config vxlan evpn_nvo add nvo vtep
$ sudo config vlan add 100
$ sudo config vlan member add -u 100 Ethernet11
$ sudo config vxlan map add vtep 100 10100

Remote VTEPs normally come from BGP EVPN. Without BGP, a remote VTEP can be added for a test directly in the application database with swssconfig in the swss container. A plain redis-cli hset is not enough: it stores the entry, but nothing tells orchagent about it.

$ echo '[{"VXLAN_REMOTE_VNI_TABLE:Vlan100:198.18.255.4": {"vni": "10100"}, "OP": "SET"}]' \
    | docker exec -i swss sh -c 'cat > /root/rvni.json && swssconfig /root/rvni.json'
$ show vxlan remotevtep
+--------------+--------------+-------------------+--------------+
| SIP          | DIP          | Creation Source   | OperStatus   |
+==============+==============+===================+==============+
| 198.18.255.2 | 198.18.255.4 | EVPN              | oper_up      |
+--------------+--------------+-------------------+--------------+

The hosts then reach each other through the tunnel (ping from one VM to the other: 5 of 5 replies, with dynamic ARP).

The L2 table shows how the SAI builds a VXLAN VLAN on this chip. VLAN 100 becomes a VPN, shown as vlan=28772 (0x7064, 0x7000 plus the VLAN), and the access port becomes a flow port in it, shown by its GPORT (0xb…) instead of a port name:

Hardware-validated

drivshell> l2 show
mac=52:54:00:d5:ca:e0 vlan=28772 GPORT=0xb0000002 port=0xb0000002(flow) Hit
mac=74:83:ef:3f:2c:fd vlan=28772 GPORT=0xb0000002 port=0xb0000002(flow) Hit
mac=e0:39:d7:88:3b:00 vlan=1 GPORT=0x0 modid=0 port=0/cpu0 Static CPU

Both MACs here are local, learned on the access flow port (the host and the attached router behind xe3). The remote host’s MAC does not appear: in SONiC’s EVPN mode the tunnel does not learn, because remote MACs are expected from BGP EVPN. Without BGP, every packet to a remote host is an unknown unicast and is flooded to the tunnel. vlan show 100 lists only the access port; the tunnel is not a member of the VLAN’s port bitmap.

Checking encapsulation in the counters

Send a known number of packets between the hosts and compare the port counters. Here 10 pings of 1000 bytes went from the sw2 host to the sw4 host and back. On sw2:

Hardware-validated

drivshell> show counters changed xe3,ce27
CLMIB_R1518.xe3          :                    10                 +10
CLMIB_RBYT.xe3                   :             2,305,788             +10,460
CLMIB_T1518.xe3          :                    10                 +10
CLMIB_TBYT.xe3                   :             2,832,665             +10,460
RTUN.ce27                :                    42                 +10
CLMIB_R1518.ce27         :                    10                 +10
CLMIB_RBYT.ce27          :             2,655,019             +11,277
CLMIB_T1518.ce27         :                    10                 +10
CLMIB_TBYT.ce27          :             2,656,835             +11,277
MC_PERQ_PKT(0).ce27      :                    26                 +10
MC_PERQ_BYTE(0).ce27     :                12,974             +10,960

  • xe3 received 10 frames of 1046 bytes from the host and sent it 10 replies of the same size.

  • ce27 sent 10 frames of 1096 bytes: the same frames with 50 bytes of VXLAN encapsulation (outer Ethernet, IPv4, UDP and VXLAN headers). They went through the multicast queue (MC_PERQ) because they were flooded (see above).

  • ce27 received the 10 encapsulated replies, and RTUN counts them as tunnel-terminated.

sw4 shows the mirror image, with RTUN on ce29:

Known problems

Traffic from the switch’s own CPU into a VXLAN VLAN (for example a ping from an address on Vlan100) does not go through the chip’s tunnel. SONiC sends it through a Linux VXLAN device, which needs its own remote entries; with the static remote VTEP above, an address on Vlan100 could not reach the remote host, and a host could not reach a remote Vlan100 address. Test with hosts on both sides.

Removing the VLAN from SONiC after the test can leave orchagent unable to finish: its log repeats removeVlan: VLAN Vlan100 still has 2 FDB entries, the VLAN stays in the chip (vlan show still lists it, with no ports), and sonic-clear fdb all does not help. Restarting swss clears it.
