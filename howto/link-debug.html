Debugging a link

This page walks through the usual questions about a front-panel link that is down, flapping or dropping packets: is there a signal, does the receiver lock, how open is the eye, what is the bit error rate, and do both ends agree on FEC and speed. It also shows how to change the transmit FIR taps, the FEC mode and the speed from the shell.

Every port on a Trident 3 is one or more lanes of an on-chip SerDes, so all of this is done with phy, portmod, ps and port. Reading is safe on a running switch. Every change on this page is made behind SONiC’s back: note the original value first, put it back when you are done, and expect a syncd restart to undo anything you leave.

Warning

Port names in the shell depend on port speeds: 100G ports are named ce, 10G and 40G ports xe and 1G ports ge, each numbered in port order. When a port changes speed class, it and the later ports of both classes are renamed (see Speed). Use port numbers, as printed in brackets by ps, in anything that changes speed or that you script.

The examples use a 100G link between two Trident 3 switches (ce27 on one, ce29 on the other, CWDM4 optics) and a 10G breakout lane on a copper DAC (xe3).

The columns that matter most:

SD

Signal detect: the receiver sees energy on the lane. 0 means no signal at all: no cable, no light, a module that is off, or a far end that is disabled.

LCK

The receiver’s clock and data recovery is locked to the incoming data.

PF, VGA, DFE

The receive equalizer: peaking filter, variable gain amplifier (0–37) and decision-feedback taps. A VGA at or near its maximum means the incoming signal is weak.

TXEQ(n1,m,p1,…)

This lane’s own transmit FIR taps: pre-cursor, main and post-cursor (see Transmit FIR taps).

EYE(L,R,U,D)

Eye margin at 1e-5 as seen by the receiver: left and right in mUI, up and down in mV. Small numbers mean a closed eye.

BER

Only filled in while the PRBS checker runs (see Bit error rate with PRBS).

How to read the combinations:

  • SD 0: nothing arrives. Check the cable or module, and that the far end is enabled and transmitting.

  • SD 1, LCK 0: something arrives but the receiver cannot lock. The ends usually disagree on the lane speed, or the signal is too poor.

  • SD 1, LCK 1 on every lane and still no link: the receivers have signal and clock recovery, but this does not establish a working PCS link or acceptable error rate. Check FEC, speed, lane mapping and link training, then inspect error counters and eye margins (see FEC).

Take two successive DSC dumps when investigating a flap. An asterisk next to SD or LCK marks a state change since the previous dump; it is not another lock level. Compare every lane. The core’s PLL_LOCK and the lanes’ receiver locks describe different parts of the signal path.

Decode UC_CFG only with the definition for the actual SerDes family and firmware. Falcon and Eagle layouts differ, so a bit position from another core can give a plausible but incorrect media or training setting. Use phy info and portmod info to identify the port’s PHY before interpreting raw fields.

phy diag … pcs prints a PCS status table, but on these switches its PCS LINK STAT column reads N even on ports that are up. Use ps and the dsc lane rows instead.

Eye diagram

portmod eyescan measures the receive eye of one lane and draws it. It takes the port number, not the name, and about 15 seconds per lane. Each character is the approximate error rate at that point as a power of ten: 7 means about 1e-7, 1 about 1e-1. The blank area in the middle is the open eye; the wider and taller it is, the more margin the link has.

Bit error rate with PRBS

A PRBS test replaces the traffic on a link with a pseudo-random pattern and counts the bit errors at the receiver. It stops all traffic on the port, so the link goes down for SONiC while it runs. Start the generator and checker on both ends with the same polynomial (p=3 is PRBS-31):

Hardware-validated: PRBS-31 on both ends, then read the checker

drivshell> phy diag ce27 prbs set p=3
drivshell> phy diag ce27 prbs get
ce27 (115):  PRBS has -2 errors!
drivshell> phy diag ce27 prbs get
ce27 (115):  PRBS OK!
drivshell> phy diag ce27 dsc

Transmit FIR taps

The transmitter pre-distorts the signal to make up for the loss of the channel. On Trident 3 SerDes it has a pre-cursor, a main and a post-cursor tap. phy control shows them as Preemphasis, packed as post << 16 | main << 8 | pre. For example 0x14410a is pre 10 (0x0a), main 65 (0x41) and post 20 (0x14), and dsc shows the same values as TXEQ(10, 65, 20, …).

With optical modules the host’s taps only drive the short electrical channel to the module, which re-times the signal. On a 100G CWDM4 link even a main tap of 20 with no pre- or post-cursor caused no errors at the far end’s PRBS checker. Tune taps on copper DAC and backplane links; on optical links look at the module instead.

Put the original value back when you are done (phy control xe3 Preemphasis=0x14410a). On SONiC the taps are normally programmed from the platform’s media settings when a module is inserted, so they may also be reset when a module is re-seated.

FEC

phy control also shows which FEC is enabled: CL74 (BASE-R FEC), CL91 (RS-FEC, the usual one for 100G) and CL108 (RS-FEC for 25G lanes). Change it with the same command:

Hardware-validated: RS-FEC on, then turned off on one end

drivshell> phy control ce27
CL74                     = False
CL91                     = True
CL108                    = False
drivshell> phy control ce27 CL91=False
CL91                     = False

Both ends must use the same FEC. With RS-FEC off on one end only, the link goes down on both ends, while the SerDes still shows signal and lock on every lane and an open eye. That combination, PMD fine but no link, is the sign of a FEC (or PCS) mismatch:

Speed

port <port> speed=<Mb/s> forces a new speed. Both ends must match, and the cable or module must support it; a 100G CWDM4 module, for example, only runs at 100G.

Changing the speed class renames ports. Setting port 1 (ce0) to 40G turned it into xe0 and shifted every other name:

Setting the interface type also reset the receive equalizer options (LP DFE) to their earlier values; check phy control too.

Putting it back

Before you leave the shell, compare each port you touched with the values you noted: ps (speed, interface, pause, link), phy control (taps, FEC, DFE) and, if PRBS ran, that prbs clear was given on both ends. SONiC does not see any of these changes and will not repair them; restarting syncd does, by re-initialising the ports from SONiC’s configuration, at the cost of a data-plane outage.
